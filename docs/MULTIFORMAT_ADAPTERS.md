# Multi-format Adapters

`rDeckForge` lets each template pack declare its own input contract and output renderer.

## Shared Core

The common pipeline is:

```text
content source(json/md or content pack) -> template input contract -> validation -> optional recipe expansion -> format adapter -> output file
```

Current shared concepts:

- `content source`: JSON or Markdown parsed into a JSON value.
- `content pack`: a directory containing `content.json`, `content.md`, or `outline.md` plus local resources such as `assets/`.
- `input.profile`: built-in content protocol shortcut. Current profiles include `teaching_deck_v1`, `design_doc_v1`, and `feature_assessment_v1`.
- `input.formats`: content formats accepted by a template pack.
- `input.schema`: template-local JSON schema file for the content structure.
- `input.schemaId`: stable identifier for the template's content protocol.
- `input.mdProfile`: optional Markdown parsing profile. Current profiles include `teaching_outline_v1`
  and `design_doc_v1`.
- `templateType`: `declarative`, `script`, or `hybrid`, allowing packs to mix built-in bindings
  with external renderer scripts.
- `renderer` + `pipeline`: executable metadata for script or mixed render flows. `script.python`,
  `script.node`, `script.shell`, `script.powershell`, and `script.command`
  renderers run from the linked template-pack folder, and pipeline steps can run after either script
  rendering or built-in PPTX/DOCX/XLSX rendering for checks, preview export, or conversions.
- `schemaErrors`: content mismatches returned by validation; render commands stop on these errors.
- `template health`: read-only Office template inspection returned by `template validate`.
- `dependencies`: optional local files, external commands, platform filters, and environment variables
  checked by `template readiness` without automatic installation.
- `tests`: optional pack-local render cases with deterministic output and Office-package assertions,
  executed by `template test` before a template is trusted by automation.
- `dataPath`: selector syntax shared by validation, planning, and rendering.
- `pages[]`: explicit PPTX page list generated by AI or external tooling. Each item declares a
  page template id and data object, then maps directly to one rendered PPT page.
- `repeat`: recipe step that expands one content collection into many output units.
- `repeat.chunk`: low-code pagination for repeated collections, so one page template can receive
  slices of an array such as 4 chapters per directory page.
- `variants`: data-driven page-template selection inside a recipe step, so a chunk with 1-2 items
  can use a different layout than a chunk with 3-4 items.
- `overflow.split`: automatic page splitting for a long nested list inside one data object, such as
  splitting a chapter's `items` into multiple content pages.
- `overflow` + `variants`: variant conditions run against the generated chunk or overflow slice, so
  tail pages can select compact layouts without a custom script.
- `steps`: grouped PPTX recipe steps, so a repeated data object can expand into multiple related
  pages before the next repeated object starts.
- `when`: conditional recipe steps, so optional sections render only when data exists, is truthy, or
  meets count rules.
- `pageTemplates` + `deckRecipes`: PPTX structural layer.
- `blockTemplates` + `documentRecipes`: DOCX structural layer.
- `sheetTemplates` + `workbookRecipes`: XLSX structural layer.
- `bindingWarnings`: format-neutral warnings for missing data, wrong types, overflow, or unsupported bindings.
- `image binding`: local resource replacement for named PPTX image placeholders.
- `table binding`: structured rows written into a named PowerPoint table placeholder, with optional layout and row style controls.
- `chartMode: "image"`: either replace an image placeholder with a local chart image or generate a PNG chart from structured labels/series data.
- `chartMode: "native"`: update a real PowerPoint chart part and its embedded workbook from structured labels/series data.

## Format Roles

### PPTX

PPTX is the first full template-rendering target.

- Template unit: `pageTemplates`
- Recipe unit: `deckRecipes`
- Output: `.pptx`
- Renderer: Node sidecar using `pptx-automizer`
- Current bindings: `text`, `list`, `image`, `backgroundImage`, `table`, and `chart` with `chartMode: "image"` or `chartMode: "native"`.
- Content-pack image paths are resolved relative to the content pack directory; SVG assets are rasterized to PNG before being embedded in generated PPTX files.
- Table data supports `columns + rows`, two-dimensional arrays, and `{ header, body }`.
- Table options support width/height fitting, column widths, row heights, table style metadata, and header/body row styles.
- Image-backed chart data supports local image `src` or generated PNG from `{ labels, series }`.
- Native chart data supports editable PowerPoint charts from `{ labels, series }`, with optional title, legend, and axis range settings.
- Template rule: private template packs stay outside the app and repository.
- Template health check: verifies source slides and named `shapeName` targets before rendering.

Next adapter step:

- Deeper native chart styling controls such as chart type conversion, colors, data labels, and multi-axis settings.
- Deeper table controls such as per-cell style maps and template-row expansion tags.

### DOCX

DOCX is a first-class document output. The first template adapter replaces text placeholders in a
linked `.docx` template pack.

Current adapter:

- Exports a minimal OpenXML `.docx` teaching handout for the demo teaching schema.
- Converts standalone Markdown engineering/design documents into DOCX through the built-in
  `design_doc_v1` profile.
- Template unit: `blockTemplates`
- Recipe unit: `documentRecipes`
- Replaces `placeholder` values such as `{{title}}` in `word/document.xml`.
- Replaces block placeholders with list paragraphs, Word tables, and local images.
- Renders semantic design-document block arrays through template-selected Word paragraph styles.
- Resolves content-pack image paths and rasterizes SVG assets to PNG before embedding.
- Preserves the placeholder paragraph properties and run properties for generated list, table,
  and image blocks.
- Supports table prototype expansion: when a table placeholder is inside a Word table, the
  generated table copies the prototype table properties, grid, row properties, cell properties,
  and paragraph/run styling while filling data rows.
- Bookmark and content-control replacement are reserved for a deeper DOCX adapter.
- Template health check: verifies placeholder strings are present in `word/document.xml`.

Next adapter step:

- Preserve and edit bookmark/content-control ranges when a template uses those Word-native features.
- Support complex Word table prototypes with merged cells, nested tables, and explicit repeated
  section markers.

### XLSX

XLSX is a first-class template-rendering target, just like PPTX and DOCX.

Current built-in adapter:

- Converts assessment JSON with `detailed_rows` and optional `summary` into a styled workbook.
- Uses a single `前端评估` worksheet with module, feature, change type, effort, dependency,
  owner, progress, and notes columns.
- Writes effort values as numeric cells and keeps the total effort as an Excel `SUM` formula.
- Adds summary rows for evaluation basis, assumptions, and out-of-scope notes.

Current template adapter:

- Template unit: `sheetTemplates`
- Recipe unit: `workbookRecipes`
- Opens a linked `.xlsx` template package and writes manifest-declared cells or named ranges.
- Expands `list` bindings vertically from the declared starting cell.
- Expands `table` bindings right and down from the declared starting cell.
- Supports manifest-ordered object columns with independent display headers through `tableColumns`.
- Supports separate header/body prototype rows through `tableBodyRowOffset`.
- Preserves existing cell style attributes on replaced cells.
- Clones row height/custom row attributes and source cell style attributes when list/table expansion creates new rows.
- Uses inline string cells while preserving untouched workbook parts.
- Accepts worksheets with default or prefixed SpreadsheetML namespaces.
- Formulas, charts, drawing/image anchors, merged ranges, and full Excel table objects are reserved for deeper XLSX adapters.
- Template health check: verifies workbook sheets, `namedRange` targets, and single-cell A1 `cell` references.

Current diagnostic adapter:

- Exports a two-sheet `.xlsx` report.
- `Content` sheet: normalized content source rows.
- `Validation` sheet: content counts, template warnings, binding warnings, and planned pages.
- This command lives under `diagnostics`, not `render`.

## CLI Surface

```bash
rdeckforge render office --template /path/template-pack --recipe any_recipe --input /path/content-pack-or-file --out /path/out.pptx --json
rdeckforge render family --template /path/template-pack --input /path/content.json --out-dir /path/outputs --base-name batch --json
rdeckforge render pptx --template /path/template-pack --recipe teaching_deck --input /path/content-pack-or-file --out /path/out.pptx --json
rdeckforge render docx --template /path/docx-template-pack --recipe standard_document --input /path/content.json --out /path/out.docx --json
rdeckforge render xlsx --template /path/xlsx-template-pack --recipe standard_workbook --input /path/content.json --out /path/out.xlsx --json
rdeckforge workflow run --template /path/template-pack --content /path/content.json --recipe teaching_deck --out /path/out.pptx --validation-out /path/validation-report.json --json
rdeckforge template contract --template /path/template-pack --out /path/template-contract.json --json
rdeckforge template content-skeleton --template /path/template-pack --mode all --out /path/content.skeleton.json --json
rdeckforge template create-script-adapter --script /path/build.py --out-dir /path/script-template-pack --id my-script-template --name "My Script Template" --format pptx --input-format md --json
rdeckforge content validate --input /path/feature-assessment.json --profile feature_assessment_v1 --json
rdeckforge diagnostics xlsx --input /path/content.json --template /path/template-pack --recipe teaching_deck --out /path/report.xlsx --json
```

All commands return stable JSON when `--json` is present.

`workflow run` is the agent-friendly validate-and-render path. It returns the full validation payload,
stable `repairHints`, and the render result when accepted. If content cannot render, it exits non-zero
with `error.code=content_validation_failed` and keeps the validation plus repair hints under `data`.
Repair hints are stable automation records with `code`, `target`, `severity`, `blocking`,
`sourcePath`, `message`, and `suggestedAction`, so an agent can route fixes without parsing prose.

`content validate` is report-oriented and returns schema errors in JSON. `render office` is the preferred accepted-output path for the app: it re-runs acceptance, reads the template format, and dispatches to PPTX/DOCX/XLSX. `render pptx`, `render docx`, and `render xlsx` remain strict format-specific commands and return a validation error instead of producing an Office file when the input violates the selected template's schema.

All Office render commands use an atomic same-directory staging file. The staged package must pass ZIP entry, XML parse, required-part, content-type override, and relationship-target validation before it replaces the requested output. Existing output survives a failed render, and successful JSON responses include an `outputIntegrity` summary.

`template contract` is the handoff artifact for AI or external scripts. It exports the accepted input
profile plus format-specific fillable units: PPTX `pageTemplates`, DOCX `blockTemplates`, and XLSX
`sheetTemplates`, including binding `dataPath`, type, required flag, and limits.

`template content-skeleton` creates a starter JSON from that contract. The `minimal` mode is useful
for quick smoke rendering; the `all` mode is useful when asking AI to map real business content into
every available template unit.

`template create-script-adapter` is the bridge for non-declarative engines. It creates a lightweight
portable pack and copies Python, Node.js, Shell, or PowerShell renderers into `renderer/` by default,
so existing skill-style renderers can be called through `render office`. Use `--link-script` when the
renderer must remain separately managed.
